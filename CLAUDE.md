# BeeVM

Group project for Advanced Cloud Computing, **Case Study 06: Lightweight MicroVM FaaS Runtime Engine**.
BeeVM is a Function-as-a-Service runtime: it runs user functions inside Firecracker MicroVMs on a bare-metal Linux node, using warm pools and snapshot restore for fast cold starts.

- Full design: `docs/architecture.md` (read it before starting a milestone).
- Progress log: `docs/progress.md` (read it first; update it at the end of every session).
- Milestone guide: `docs/milestones.md` (13 session-sized milestones; this supersedes the 9 milestones listed in the architecture doc).
- Case study source: `Advanced Cloud System Software Design_ 30 Case Studies.docx`. Only group 06's title, summary and overview-table row are valid. Its detailed sections 1–5 are a copy-paste error about an HNSW vector engine — ignore them.

## Grading criteria (from the case study)
- Cold-start latency **< 50 ms** (via snapshot restore)
- Tenant isolation, verified by tests
- MicroVM density per node

## Decisions (do not change without asking)
- Control plane in **Go** (1.24+; installed 1.27.3), `firecracker-go-sdk` (pinned to a main-branch commit, see `go.mod`; last tag is from 2022), `go-chi/chi`, SQLite via `modernc.org/sqlite`.
- Host ↔ guest communication over **vsock**, not the network.
- **One network namespace per VM**, so restored snapshots can keep the same guest IP.
- Snapshots live on **local NVMe**; S3/MinIO is only the source and backup.
- Guest runtimes: **Python 3.14, Node.js 24, static binaries**; Alpine 3.24 rootfs, `vmlinux` 6.1. (Changed from 3.12/20 with the user on 2026-11-05: Alpine 3.24 does not ship them and Node 20 is end-of-life.)
- Isolation: Firecracker **jailer**, cgroups v2, seccomp, nftables between tenants.
- Web dashboard (`web/`) and Prometheus/Grafana (`deploy/monitoring/`) are **optional and swappable**: they only use the public REST/SSE API and `/metrics`. Core code must never import them.
- Component names: API Gateway & HTTP Router, Function Registry, Scheduler & Warm Pool, Snapshot Manager, VM Manager, Isolation & Network, Observability.

## Environment
- Windows 11 host; code runs inside **WSL2 Ubuntu 24.04**.
- `/dev/kvm` exists in WSL (owned by `root:kvm`); the user must be in the `kvm` group (done in milestone 1 setup script).
- Final benchmarks on a cloud Linux node with nested virtualization or a short bare-metal (i3en.metal) run.

## Commands
Run everything from a **WSL terminal** inside this folder (`/mnt/c/Users/ommga/Desktop/ACC/BeeVM`). Source code stays on Windows; big files (kernel, rootfs, snapshots, run folders) live in `$BEEVM_HOME` (default `~/.beevm`) on the fast WSL disk.

- `make setup`: one-time, re-runnable install of Go, Firecracker, kernel and rootfs (asks for sudo).
- `make images`: rebuild kernel and the three rootfs images (no sudo): `rootfs.ext4` (binaries), `rootfs-python.ext4`, `rootfs-node.ext4` (`make rootfs|rootfs-python|rootfs-node` for one). Runtime packages come from Alpine via `apk.static --root` under fakeroot; versions pinned by major in `scripts/common.sh`, installed versions in the image's `/etc/beevm/versions`. Alpine keeps only the newest build: if the `apk-tools-static` download 404s, update `APK_STATIC_VERSION/SHA256`.
- `make boot`: boot a MicroVM and get a shell (`reboot -f` to exit).
- `make boot-test`: boot automatically, check it worked, print boot time.
- `make clean-images`: delete images and run folders.
- `make build`: build `bin/beevmd` (server) and `bin/beevm` (user CLI).
- Run the service: `./bin/beevmd tenant add <name>` (prints the API key once; also `tenant ls`, `key add|ls|revoke`), then `./bin/beevmd serve [--addr 127.0.0.1:8080] [--max-vms 8]`. Users: `export BEEVM_API_KEY=...`, then `beevm deploy <name> <binary>`, `beevm invoke <name> --payload '{...}' [-v]`, `beevm ls`, `beevm rm <name>`. API: `PUT /api/v1/functions/{name}` (multipart), `POST /invoke/{name}`; keys go in `Authorization: Bearer`.
- Artifact store (optional, S3 API): `make minio` (local MinIO built from pinned source, no Docker; `make minio-up` for Docker Compose), then `set -a; . deploy/minio.env; set +a` before `beevmd serve` (reads `BEEVM_S3_BUCKET`, `BEEVM_S3_ENDPOINT`, `BEEVM_S3_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`; or the `--s3-*` flags). No bucket = code on local disk only. `functions/<sha256>` then acts as a cache of the bucket. `make test-s3` runs the store tests against the running MinIO. `beevm invoke -v` shows cache hit/miss.
- Data lives in `$BEEVM_HOME`: `beevm.db` (SQLite registry), `functions/<sha256>` (code cache; source of truth is S3 when configured), `snapshots/<key>/` (runtime snapshots: `vmstate`, `mem`, `meta.json`; `snapshots/fn-<key>/` function snapshots, ~memory size each on disk), `run/serve/` (the server's VM folders, cleared on start), `run/vms/` (`boot`/`invoke` commands), `run/bench/`.
- `./bin/beevmd boot [--hold 30s] [--keep-logs]`: boot one VM through the Go code, show console, stop, clean up.
- Runtimes (M8): `beevm deploy <name> <binary|folder|file.py|file.js|pkg.zip> [--runtime binary|python|node] [--handler module.func|file.func]` (runtime detected: `handler.py` -> python, `index.js` -> node, ELF -> binary; folders and single files are zipped by the CLI; defaults `handler.handler` / `index.handler`, a single file `app.py` -> `app.handler`). Python/Node code is a zip package (rules in `internal/pkg`: no absolute paths, `..`, symlinks; max 2,000 files, 32 MiB unpacked) unpacked by the agent into `/run/beevm/code`; a long-lived shim (`guest/shims/{python/shim.py,node/shim.js}`, talks JSON lines on fd 3/4) imports it once and calls `handler(event)` (or `(event, context)`). Agent endpoints `PUT /package`, `POST /load`. Function snapshots: after a deploy (and after a call that had to import) the runner builds `snapshots/fn-<key>/` in the background (restore runtime snapshot, upload, import, settle 200 ms, snapshot; one build at a time); new VMs then restore with the code inside (`X-BeeVM-Snapshot: function`, upload/load 0). Redeploy/delete removes them; `serve` removes orphans at start. `beevm invoke -v` shows snapshot kind and load ms; `beevmd snapshot build --runtime R`, `snapshot ls` shows KIND/RUNTIME/FUNCTION; `beevmd invoke --code examples/functions/hello-python`; `bench coldstart --code examples/functions/hello-node --mode boot,restore,function,warm`.
- Isolation (M9): `sudo ./bin/beevmd serve --isolation jailer [--egress none|nat] [--cpu-limit 100] [--uid-base 900000] [--net-prealloc N]` (also on `invoke`, `bench coldstart`, `snapshot build`; default `--isolation none` = old unprivileged behaviour). Under sudo `BEEVM_HOME` comes from `SUDO_USER`'s home; root-created files in it are chowned back at start/exit. Per VM: jailer (chroot in `$BEEVM_HOME/jail/firecracker/<id>/root`, kernel/rootfs/snapshot hard-linked in, UID/GID 900000+slot, seccomp on), cgroup `/sys/fs/cgroup/beevm/t<tenant>/<vm>` (`memory.max` = guest + 64 MiB, `pids.max` 32, `cpu.max` = vCPUs x cpu-limit %), netns `beevm-<slot>` with `tap0` (guest 172.16.0.2, same in every VM) NATed to clone IP `10.200.x.(4n+2)`; host nft table `ip beevm`: per-tenant address sets, only same-tenant VM traffic, VM->host dropped; forwarding only on `bv<n>` links (global `ip_forward` untouched unless `--egress nat`). Code: `internal/vmm/jail.go` (mechanism, `vmm.Isolator` interface), `internal/isolation` (Manager: slots, cgroups, lock `/run/beevm/isolation.lock`, stale cleanup), `internal/netns` (namespaces, nftables). Snapshot keys get `Isolation` (omitempty, so `none` keys are unchanged). Guest (all modes): functions run as user `fn` (uid 1000), RLIMIT_NPROC 256, agent `oom_score_adj` -1000, leftover `fn` processes frozen and killed after each call, `/tmp` tmpfs capped at 25 %. Attack functions `examples/functions/{forkbomb,memhog,cpuhog,netprobe,hostread}`. `make test-isolation` (compiles tests as you, runs them with sudo; `RUN=regexp`) writes `bench/results/isolation-<time>.md`. `beevm vms` shows each VM's ADDRESS.
- Observability (M10): `beevmd serve` serves Prometheus metrics at `GET /metrics` on `--addr` (no API key; shows tenant/function names, so keep `--addr` on localhost; `--metrics=false` turns it off), `--log-level debug|info|warn|error`, `--log-format json|text`; request log lines carry `request_id`, `function`, `runtime`, `start`, `snapshot`, `boot_ms`, `upload_ms`, `load_ms`, `function_ms`. Metrics (`internal/metrics`, own registry): `beevm_invocations_total{tenant,function,runtime,start,status}`, histograms `beevm_invoke_duration_seconds{start,runtime}`, `beevm_vm_ready_seconds{start,snapshot}`, `beevm_upload_seconds`, `beevm_load_seconds`, `beevm_function_seconds`; `beevm_code_fetches_total`, `beevm_vm_recycled_total{reason}`, `beevm_snapshot_builds_total` / `_build_seconds`; read at scrape time by `PoolCollector`: `beevm_vms{state}`, `beevm_vms_max`, `beevm_vm_memory_{rss,pss}_bytes{state}` + `beevm_vm_memory_measured_vms` (from `/proc/<pid>/smaps_rollup` of each Firecracker process), `beevm_node_memory_{total,available}_bytes`. Hooks (all optional): `pool.Config.OnRecycle`, `pool.VMInfo.PID` via `pool.PIDer`, `snapshot.Manager.SetObserver`, `api.Deps.Metrics`. Optional module: `make monitoring` (pinned Prometheus 3.15.1 + Grafana 13.3.0 tarballs in `$BEEVM_HOME/monitoring`, no Docker; Prometheus `127.0.0.1:9090` scrapes `127.0.0.1:8080` every 1 s, Grafana `http://localhost:3000` dashboard "BeeVM", anonymous view, admin/admin to edit); untested Compose profile `make monitoring-up`; files in `deploy/monitoring/`, `scripts/monitoring.sh`. Load: `beevmd bench load --fn a,b --rate 20 --duration 2m --concurrency 8 [--out bench/results]` (needs `BEEVM_API_KEY`; open loop, round-robin, skipped calls counted).
- Web dashboard (M11, optional module): `make ui` (Node 24.22.2 pinned in `$BEEVM_HOME/node-<ver>` by `scripts/ui.sh`, `npm ci`, type-check + Vite build into `web/dist`), `make ui-dev` (Vite on `127.0.0.1:5173/ui/`, proxies `/api`, `/invoke`, `/healthz` to :8080), `make test-ui` (Vitest). `beevmd serve --ui-dir web/dist` (default; relative to the cwd, empty = off) serves it at `http://127.0.0.1:8080/ui/` (no `go:embed`; logs "web dashboard not built" without it). The page asks for an API key (sessionStorage). Core API added for it: `GET /api/v1/events` (SSE, key group, own tenant only: `hello` {vms, max_vms} first and again after lag, `vm` (apitypes.VM + `prev_id`, state `destroyed` = gone), `invoke` (apitypes.InvokeEvent), `: ping` every 15 s) and `GET /api/v1/node` (whole node: `max_vms`, `vms`, `tenant_vms`, `states`, PSS/RSS sums, node memory). Hub `internal/events` (Publish never blocks; closed on shutdown via `srv.RegisterOnShutdown`), hook `pool.Config.OnStateChange` (`api.VMEvents(hub)`). Dashboard code: `web/src/{api,sse,state,stats}.ts`, `web/src/components/`. Remove the module: delete `web/`, `scripts/ui.sh`, the Makefile `ui` block.
- Warm pool (M7): `beevmd serve` uses `--runner warm` by default: after a call the VM stays idle for `--keep-alive` (default 60s) and the next call of the **same function** (same tenant, function, code and size; never shared across functions) reuses it (`X-BeeVM-Start: warm`, no restore, no upload). New VMs are restored from the base snapshot. `--max-vms` counts VMs in every state (idle too); when full, the least recently used idle VM is evicted. Timeouts, agent errors and abandoned calls throw the VM away; a normal function failure keeps it. Redeploy/delete drains the function's VMs. `beevm prewarm <name> -n N` (`POST /api/v1/functions/{name}/prewarm?count=N`) starts idle VMs; `beevm vms` (`GET /api/v1/vms`) lists your VMs and states. Code: `internal/pool` (state machine `Restoring → Idle → Busy → Recycling → Destroyed`, no Firecracker imports), `runner.WarmRunner`.
- Snapshots (M6): `--runner snapshot` restores every call from a base snapshot (builds the 128 MiB/1 vCPU one at start-up; falls back to booting if a build fails); `--runner cold` boots every call. `./bin/beevmd snapshot build [--mem N --vcpus N] | ls | rm <key> | rm --stale`. A snapshot's key hashes Firecracker version, kernel, rootfs, memory, vCPUs, boot args and `snapshot.BuildVersion` (bump it when `buildVM` changes), so `make images` automatically makes old snapshots stale. `./bin/beevmd invoke --restore ...` restores instead of booting. `beevm invoke -v` shows `restore`/`boot` and the ready/upload times.
- Benchmark: `./bin/beevmd bench coldstart [--runs 100] [--mode boot,restore,warm]` (warm = repeat calls through the real warm pool, only "first response") prints p50/p90/p99/max per phase and writes `bench/results/coldstart-<time>.{csv,md}` (git-ignored). Restore rows: spawn, load, agent (until `/resume` answered), page faults of the firecracker process. Tuning flags: `--probe resume|health` (health = old two-request way), `--fc-metrics` (Firecracker's own load time), `--cold-cache` (drop files from the page cache before every run; not while `serve` runs), `--settle D` (throw-away snapshot with another settle time), `--gap D`, `--pin CPUS`, `--mem N`.
- Restore status (M6 refine, 2026-11-02): p50 ~45 ms, p99 60-67 ms on WSL2 (KVM load noise + ~37 µs page faults under nested virtualization). userfaultfd page prefetch is deferred to the cloud node: on WSL `/dev/userfaultfd` is root-only and we chose not to loosen it. Details: `developer-guide/guide.md` 8.10-8.11.
- Benchmark in **Legion Performance Mode, plugged in**: Balance mode/battery makes everything ~2x slower (boot 1.8 s instead of 0.94 s).
- All VMs share one read-only rootfs (`SharedRootfs`); `/run` and `/tmp` in the guest are RAM. Firecracker runs inside each VM folder and the vsock socket path is relative (`v.sock`), so restored VMs get their own socket.
- `make examples`: build example functions (static) into `bin/functions/`. `./bin/beevmd invoke --code bin/functions/hello-go-binary --payload '{"name":"Om"}' --repeat 5`: boot a VM with the guest agent, upload the binary, run it, clean up.
- The guest agent (`cmd/beevm-agent`) is built into the rootfs by `make rootfs` / `make images`; rebuild images after changing agent code.
- `make test`: Go unit tests (no KVM). `make test-kvm`: tests that boot real VMs (`//go:build kvm`), all packages including the end-to-end API test. `make vet`: go vet.
- Calling `go` from Windows tools via `wsl.exe` mangles quotes and `$VARS`; put multi-line commands in a script file and run `wsl.exe -- bash <file>`, or use `make`.
